# Toggle-preserving GPU LM — 2026-09-21

Secant-SR can now fit coefficients with GPU Levenberg–Marquardt before breeding.
The scorer, Secant AST encoding, SASS specializer and module pipeline are unchanged.
The fitting service is in `toggle/include/secant_sr_lm.h`; it contains no GP policy.

## Contract

1. Create a persistent fitting handle from the search configuration and **training**
   input/target arrays. It compiles its reusable kernels once, retains the CUDA
   primary context, and allocates data/work pools, an owned stream and events.
2. Submit a bounded cohort of scored genomes and their source coefficient bank.
   The incumbent toggle binding is included. Additional bindings uniquely sample
   assignments of used toggle bits; unused bits do not multiply fitting work.
3. Start zero preserves each binding's coefficient centers. Other starts use a
   replayable Philox bank with three jitter scales. Fixed literals are unchanged.
   Raw references sharing a slot remain tied; fitted references sharing a slot and
   exact value bits remain tied. Independent equal-valued parameters stay separate.
4. Each binding fits at most eight active parameters. Wider bindings rotate explicit
   blocks by sequence, preserving other centers and reporting blocked bindings.
5. Fit results are **proposals**. The CLI runs the normal native-SASS scorer over
   every toggle binding using one bank, because fitted values are embedded. Only
   strict improvements are accepted into the population. Final CPU replay and
   held-out validation remain mandatory. No holdout data enters fitting/selection.

No per-fit memory allocation is required by the fitting service. Ordinary completion
waits on owned events. A full owned-stream synchronization is used only for error
recovery. Unknown completion retains resources for retry/worker termination; it
does not free buffers beneath pending GPU work. There is no CPU optimizer fallback.

## Kernel implementation and limits

This version interprets postorder **operators** on the GPU. It is not the historical
settings-based LM or a SASS-specialized derivative evaluator. Postfix intermediate
values use fully unrolled, fixed-position registers. The stack capacity is bounded
at initialization by `min((max_nodes+1)/2, max_depth+1)` (minimum allocation two).
Host validation enforces those limits before submission.

Programs are grouped into 1/2/4/8-parameter shapes without changing model/binding/start
indices. Shapes 1/2/4 use one lane per row; shape 8 shares a row across two lanes.
Analytic forward derivatives feed double-precision SSE, Jᵀr and JᵀJ accumulation.
The damped Cholesky solve is unrolled in registers. Nonfinite trials are rejected.
All production kernels must have zero local bytes or initialization fails explicitly.
The zero-local guarantee was tested on rack1's RTX 5080 / CUDA 13.1; another toolkit
or architecture must pass the same guard. Register counts depend on requested limits.

This is still an optimization target: register-only interpretation is not a claim
of peak SASS throughput. Resource-limited resident blocks are reported; they are
not a measurement of achieved occupancy. Broader row/state/parameter scaling remains
to be profiled.

## Controls and accounting

```
--lm-iterations 4 --lm-budget 512 --lm-bindings 32 --lm-starts 4
--lm-parameters 8 --lm-interval 1 --lm-scale 1 --lm-threads 64
```

Defaults leave LM disabled (`--lm-iterations 0`). `--refine-rounds` must be zero
when LM is enabled. The controller selects the best distinct eligible genomes
by training SSE; this is an explicit initial policy, not an optimal diversity rule.
Four iterations mean an initial statistics pass plus four proposal evaluations.
The wall-time budget includes setup and is checked between LM iterations and GP
generations. Completing the current pass and native rescoring can overrun it.

Results retain LM setup/NVRTC, device, rescore and total times, promotions, binding
and state counts, invalid evaluations, parameter-block counts, and per-shape
register/occupancy limits and work counts. `row_evaluations` counts attempted
rows, including early exits for invalid domains. It is separate from broad-search
configurations. `incumbent` JSONL records retain resolved ASTs and elapsed times
for later shorter-budget analysis; they are not resumable GP-population checkpoints.

## Measured development deviations

The first working evaluator used dynamically indexed local arrays. It was a
correctness reference, not an approved final kernel. NVRTC reported **896 bytes
local stack, zero spill stores/loads, 40 registers** in statistics; the solve used
576 local bytes. The first register-only replacement removed that storage but
forced small fits through an eight-parameter footprint and was about five times
slower. It was rejected before any long campaign.

Grouping by active parameter count repaired that regression. On the same first
generation, 512 selected genomes, up to 32 bindings × four starts, four proposals,
10,000 training rows, RTX 5080:

| Prepared dataset, seed 860 | Local-array reference | First zero-stack attempt | Grouped register kernels |
|---|---:|---:|---:|
| Feynman III.7.38 | 66.3 ms | 318.4 ms | 52.6 ms |
| Feynman I.6.2 | 49.5 ms | 264.1 ms | 42.1 ms |

These are fitting-stage elapsed times including native rescore, excluding setup
and broad scoring. Both final validation MSEs matched the reference. This is a
two-workload check, not a broad speed claim; different derivatives/reduction order
can produce slightly different accepted intermediate coefficients. Cold grouped-LM
NVRTC was about 0.78 s in this check, versus about 0.23 s for the initial evaluator;
warm compiler-cache behavior must not be presented as cold compilation.
The [retained measurements](data/toggle-lm-profile-20260921.json) include the
reference, rejected attempt, repaired implementation and final resource checks.

The four-fit, 30-second reference preflight completed with three held-out R²>.999
successes (two passed the stricter native train/holdout threshold). Its result copy
initially failed because rack1 lacks rsync. The artifacts were recovered through
SSH/tar, the worker was repaired to use those existing tools, and a corrective
Telegram message was delivered. No fit result was lost or rerun to hide the error.

## Verification and next experiment

Host tests cover binding uniqueness, incumbent inclusion, parameter identity,
fixed literals, deterministic starts, alias rejection and wide-model block rotation.
GPU checks cover all 14 derivative operators against central differences, shared
nonlinear parameters, domain rejection, linear/nonlinear convergence, mixed
two/four-way toggles, odd row tails, native rescoring, GP acceptance, a maximum
63-node/32-leaf postfix stack, and an eight-parameter rank-deficient fit.

`bench/lm_quality/campaign.py` prepares the quality run: 21 existing diagnostic
problems × two data/search seeds × two repeats = 84 fits, up to 900 seconds each,
population 8192, with LM feedback every generation. Both rack1 GPUs can split it.
Identity hashes, replayable winners, improvement histories, errors and budget
overruns are retained. It is a diagnostic subset, not a new full-SRBench result.
Lifecycle Telegram notifications attach to mac1 tmux workers independently of an
assistant turn. Mac1 must remain online for this campaign's SSH/notification setup.

Completed at `runs/lm-quality-20260921/` on mac1 and
`/home/cdurham/experiments/secant-toggle-lm-20260921/quality` on rack1. All 84 fits
finished without execution errors; 52 passed held-out R² > .999 and 29 passed both
native training/holdout thresholds. Both Telegram notifications were accepted.
All CPU score audits passed and local bytes remained zero. Campaign elapsed was
7 h 3 min 47 s across two GPUs; LM accounted for 72% of summed fit time.
The source archive and executable hashes are retained beside the remote run.
See the [complete results and unequal-budget comparison](toggle-lm-results-20260922.md)
before interpreting this as an improvement over historical LM: the old quality
gap remains despite the larger allowance.
