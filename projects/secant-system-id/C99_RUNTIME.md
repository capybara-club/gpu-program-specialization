# C99 specialization and eager CUDA runtime

## Purpose

The C99 runtime is the execution boundary used by the GP loop. Python compiles
and inspects a template once, then makes one call for a complete search. C
neither parses Python objects nor consumes JSON while searching.

## Flat population ABI

A submission borrows three contiguous arrays:

```text
ssid_genome_desc[]  -> ranges in ssid_ast_desc[]
ssid_ast_desc[]     -> site index and range in program_bytes[]
program_bytes[]     -> encoded postorder instructions
```

Each genome contains exactly one AST for every missing site. AST order is not semantically significant because every AST carries an explicit `site_index`. This keeps crossover and mutation independent for each missing equation while allowing the specializer to emit all outputs into one packed genome body.

The Python `FlatGenomeBatch.from_genomes` helper constructs these arrays. `FlatGenomeBatch.from_raw` accepts already-generated byte streams without constructing `Program` objects. The buffers are borrowed rather than copied and must remain alive until the returned ticket completes.

## Template metadata boundary

Python still generates CUDA, compiles it, and inspects the resulting CUBIN. The inspection result is converted once into `ssid_template_desc` and `ssid_packed_kernel_desc` structures. `ssid_template_create` validates and deep-copies the CUBIN and every variable-length metadata array.

JSON remains the human-readable inspection and reproducibility format. It is not parsed by the C99 specializer or runner. A future standalone C executable can receive the same structures from a compact binary sidecar or generated C data without changing the runtime ABI.

## One fixed CUBIN copy per worker

At pipeline creation, every specialization worker allocates exactly one writable buffer whose size equals the immutable template CUBIN. For every job, the worker:

1. copies the immutable template into its own buffer;
2. assembles every postorder AST directly into the appropriate packed arena;
3. rewrites branch targets and register-count metadata; and
4. publishes that exact-size buffer to the CUDA-owner thread.

The worker waits only until `cuModuleLoadData` returns. CUDA has consumed the image by then, so the worker can immediately overwrite its host buffer for the next specialization while the loaded module remains resident or executes on the GPU.

## Single-context eager pipeline

One dedicated thread owns one CUDA context and a configurable pool of
nonblocking execution streams. CPU specialization workers never create or use
CUDA contexts. For a module containing multiple packed kernels, the CUDA owner
distributes those kernels round-robin across the streams, records one dependency
event per used stream, and makes the module's reduction/completion stream wait
for every scoring stream before reducing winners. The CUDA thread repeatedly:

1. loads the next ready specialized CUBIN;
2. resolves every populated packed kernel entry point;
3. launches those entry points across the configured streams;
4. joins scoring streams with events and records one module completion event;
5. begins loading later ready modules while earlier kernels execute; and
6. unloads each module only after its event completes.

The `maximum_loaded_modules` setting bounds resident or in-flight modules and
must be at least the execution-stream count. A value of one for both is the
serial reference shape. Larger values permit eager loading and host/device
overlap. The queue is also bounded so GP cannot create unlimited specialized
modules when loading or execution is the bottleneck.

Pipeline state is conceptually:

```text
PENDING -> SPECIALIZING -> READY_TO_LOAD -> IN_FLIGHT -> COMPLETE
```

Failures are attached to the job ticket. Module lifetime extends through the final kernel completion event, never merely through the host launch call.

Pending jobs use a separate worker condition variable and wake one specialization worker per submission. CUDA-ready work has its own notification path. This avoids waking every CPU worker for every submitted or completed ticket when the pool is large.

## Search-result reduction

The launch ABI supports two output modes. `SSID_OUTPUT_FULL_MSE` preserves one
MSE value for every `(genome, setting)` pair and is the reference/debug path.
`SSID_OUTPUT_GENOME_WINNERS` keeps the search result on the GPU: every scoring
CTA reduces its setting tile to one `(score, setting_index)` pair, then the
ordinary fixed CUDA kernel `ssid_reduce_winners` reduces those tile winners to
one pair per genome.

The final setting index identifies the winning constant and leaf-binding row in
the resident settings arrays. No AST rewrite is required before the GP loop
decides whether to retain that candidate. Each in-flight ticket receives its
own CTA-scratch and final-output slice; the module's completion event covers
both scoring and reduction before either slice is reused.

Both scoring and reduction block sizes must be powers of two. A partial final
setting tile is represented by an infinite sentinel score, so arbitrary
positive setting counts remain valid.

## Building and testing

The runtime uses only the system C compiler, POSIX threads, dynamic loading, and the installed NVIDIA driver:

```sh
make c99
PYTHONPATH=src python3 -m unittest tests.test_c_runtime -v
```

The CPU-only test constructs a synthetic two-kernel CUBIN plan and verifies that the C99 output is byte-for-byte identical to the Python specializer, including every currently supported FP32 postorder operation. It also runs the worker pool with configurable thread counts without requiring a GPU.

`ssid_benchmark_specialization_raw` and `C99Template.benchmark_raw` measure the assembler and exact-size CUBIN copies without Python submission, ticket allocation, queueing, or CUDA work. The benchmark creates one reusable CUBIN buffer per POSIX worker, synchronizes their start, and reports module, genome, AST, and CUBIN-byte throughput. It is intended to separate specializer scaling from control-plane overhead; the eager pipeline remains the end-to-end measurement.

The end-to-end benchmark compiles a real module, constructs a flat AST byte stream, sweeps specialization workers, and runs the eager single-context CUDA pipeline:

```sh
PYTHONPATH=src python3 -m secant_system_id.cli fedbatch-c99-pipeline-run \
  --arch sm_89 --kernels 2 --genomes 16 --genome-capacity 8 \
  --settings 2048 --workers 4 --worker-counts 1,2,4,8 \
  --specialization-submissions 5000 --submissions 32 --loaded-modules 8
```

The JSON result separates CUDA compilation, direct Python and C99 specialization, worker scaling, module loading, function lookup, kernel launch, total eager-pipeline throughput, and CPU/GPU score agreement.

The same CUDA-owner machinery also accepts fixed-size, already-specialized
trajectory-LM CUBINs through `ssid_module_pipeline_create` and
`ssid_pipeline_submit_trajectory_lm`. Python still generates the split primal
and derivative SASS, but it submits a whole promotion batch to one persistent
loader rather than creating one CUDA context, module, and set of allocations
per promoted genome. Starts and bindings are uploaded as contiguous candidate
slabs, the dense reference is uploaded once, and output buffers are reused for
the lifetime of the campaign. Every ticket receives disjoint input/output
offsets and retains its source CUBIN until the worker has copied it.

The direct and queued LM paths can be compared with:

```sh
PYTHONPATH=src python3 examples/benchmark_trajectory_lm_queue.py \
  --arch sm_89 --candidates 4 --settings 8192 --starts 4
```

The benchmark compares every fitted constant, MSE, iteration count,
accepted-step count, and best-fit index before reporting queue throughput and
per-ticket module-load time.

`fedbatch-c99-unique-sweep` is the stricter throughput benchmark. It creates a
deterministic but byte-distinct genome batch for every submission, specializes
and hashes every CUBIN before timing, and rejects the run unless the requested
number of hashes are unique. It can sweep settings counts and eager depths in
either full-MSE or compact-winner mode:

```sh
PYTHONPATH=src python3 -m secant_system_id.cli fedbatch-c99-unique-sweep \
  --arch sm_120 --genomes 128 --genome-capacity 128 --genomes-per-cta 1 \
  --settings-counts 256,512,1024 --loaded-module-depths 1,2,3 \
  --threads 256 --workers 1 --submissions 512 --winner-output
```

Batch construction and the one-time uniqueness check are deliberately reported
but excluded from the timed eager pipeline. This isolates the C99
specialize/load/execute/reduce/readback path. `fedbatch-c99-gp-run` is the
corresponding production-style measurement: it generates and evolves the flat
AST arrays in C inside the timed loop.

## C99 GP integration

`ssid_gp_create` allocates two fixed population arenas and all AST annotations,
settings incumbents, scratch buffers, and archive storage. `ssid_gp_run` then
executes all generations while calling the same eager pipeline used by the raw
benchmarks. The GP produces module-sized batches, waits for their reduced
winners, inherits the winning constants and bindings, and advances the
population without re-entering Python.

Search templates use the explicit `SSID_SETTINGS_HASHED_INCUMBENT` mode. The
GPU deterministically derives each setting from a compact incumbent row; the
host uses the same function only for the winning row. Ordinary templates use
`SSID_SETTINGS_MATERIALIZED`. The runtime rejects the wrong mode at the GP
boundary. `SSID_OUTPUT_FULL_MSE` remains unchanged for runs that need every
score rather than only the winning pair.

## Current scope

- **Known hot-path deviation:** `ssid_specialize_kernel` currently allocates
  its temporary packed-body offset array with `malloc` for every kernel
  specialization and frees it afterward. This is correctness-preserving, and
  existing C99 specialization measurements include that allocator traffic, but
  it does not satisfy the intended worker-owned arena/scratch design. Move this
  array into fixed per-worker scratch sized from `genome_capacity`, then rerun
  specialization and eager-pipeline throughput measurements.
- Packed multi-kernel modules only; direct single-site templates still use the Python runtime.
- Dense, aligned fed-batch launch ABI.
- FP32 postorder SASS on `sm_89`, `sm_90`, and `sm_120`.
- One CUDA context and a configurable number of execution streams; one stream
  remains the default for existing callers.
- Settings, bindings, references, and output buffers remain resident on the GPU across module submissions.
- The compact binary metadata sidecar remains a subsequent layer; the in-memory C ABI is already independent of Python.
- The C99 GP is a minimal generational baseline. Blinded recovery and selective
  trajectory-LM promotion are available as experiments. LM SASS specialization
  remains in Python, while module loading, launch, completion tracking,
  unloading, and fixed device-buffer ownership use the eager C99 pipeline.
