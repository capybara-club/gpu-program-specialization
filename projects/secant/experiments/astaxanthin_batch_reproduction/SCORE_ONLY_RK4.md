# Score-only RK4 throughput

This benchmark measures the native-CUDA execution shape that precedes LM or
structure specialization. It evaluates the two published rate laws directly;
there is no AST interpreter, LM, sensitivity propagation, Gram accumulation,
linear solve, or parameter update.

## Work represented by one trajectory

One CUDA thread:

1. loads one six-constant rate-law setting from a structure-of-arrays buffer;
2. selects one of the three published experimental initial conditions;
3. integrates the four-state system from 0 to 96 hours with fixed-step RK4;
4. scores all four state channels at 12 observation times; and
5. writes one trajectory MSE.

`blockIdx.x` tiles settings and `blockIdx.y` selects the trajectory. Thus all
threads in a CTA read the same initial condition and target at a given point,
while their six setting loads remain coalesced. The 12 initial-state values and
144 targets occupy 624 bytes of CUDA constant memory. No shared memory is used.

Setting zero contains the published vector
`[0.43, 63.7, 5.8, 0.132, 3.68, 0]`. Its three final states are compared with
the independent double-precision CPU integrator. The target table itself is
generated by that CPU reference with a 0.01-hour maximum step.

The timed region contains only repeated kernel launches. Context creation,
module loading, target and setting upload, warmup, and result copies are
excluded. The CUBIN is compiled with NVRTC `--use_fast_math`, matching the
existing resident-LM experiment's compilation policy.

## Measured results

The saturated comparison used 262,144 settings, or 786,432 independent
trajectory runs per launch.

| GPU | Steps / 8 h | RK4 steps / trajectory | RHS evaluations / trajectory | CTA threads | Kernel ms / launch | Trajectories/s | Complete 3-trajectory settings/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| RTX 5090 | 16 | 192 | 768 | 64 | 0.3480 | 2.260e9 | 7.533e8 |
| RTX 4090 | 16 | 192 | 768 | 256 | 0.5048 | 1.558e9 | 5.193e8 |
| RTX 5090 | 80 | 960 | 3,840 | 128 | 1.7423 | 4.514e8 | 1.505e8 |
| RTX 4090 | 80 | 960 | 3,840 | 128 | 2.5175 | 3.124e8 | 1.041e8 |

The final column is the trajectory throughput divided by three. It is a useful
throughput-equivalent rate for a setting evaluated on all three experiments,
but the current kernel writes three separate MSEs and does not include their
final reduction.

The corresponding sustained RHS rates were 1.736e12/s on the 5090 and
1.196e12/s on the 4090 at the 16-step setting. The 80-step results were
1.733e12/s and 1.200e12/s, showing that the longer integration remained in the
same compute-throughput regime.

## Resource and correctness checks

Both architecture-specific CUBINs use:

- 38 registers per thread;
- zero stack bytes;
- zero spill loads and stores;
- zero local-memory bytes; and
- zero shared-memory bytes.

The `sm_89` SASS contains exactly six `LDG.E.CONSTANT` setting loads before the
integration loop and no further global setting loads inside it. The six values
therefore remain in registers for the entire trajectory, as intended.

At 16 steps per observation interval, the planted setting's trajectory MSEs
against the 0.01-hour reference targets were `9.44e-13`, `4.87e-12`, and
`4.82e-13`. Across all three trajectories and four final state components, the
maximum final-state error against a same-step double CPU run was `4.14e-6`
absolute and `2.63e-7` after scaling by `max(abs(reference), 1)`. Verification
passed on both GPUs.

## Saturation observations

At 16 steps per observation interval and 128 CTA threads:

| Settings | Trajectories / launch | RTX 5090 trajectories/s | RTX 4090 trajectories/s |
| ---: | ---: | ---: | ---: |
| 8,192 | 24,576 | 1.164e9 | 9.360e8 |
| 65,536 | 196,608 | 2.100e9 | 1.525e9 |
| 262,144 | 786,432 | 2.170e9 | 1.550e9 |
| 1,048,576 | 3,145,728 | 2.083e9 | 1.554e9 |

The 5090 was narrowly best with 32-64 threads per CTA in the measured sweep;
the 4090 was essentially insensitive from 32 through 256 threads. A default of
64 or 128 threads is reasonable.

## Scope boundary

Despite sometimes being called the fed-batch example in discussion, the
reproduced Riezzo et al. benchmark is a **batch** model: it has no feed-rate
input or changing-volume state. This kernel is the correct benchmark for the
current astaxanthin reproduction. A genuine fed-batch extension will add the
feed schedule, dilution terms, volume dynamics, and potentially unaligned
observation events; it should receive a separate benchmark rather than silently
changing this one.
