# FusedSINDy

> **Collection category:** Fused statistics and fitting research. See the [project map](../../docs/PROJECTS.md) for entry points and status, and [research coverage](../../docs/RESEARCH_COVERAGE.md) for limitations.

CUDA-fused sparse equation discovery from PyTorch tensors, without
materializing generated feature matrices.

FusedSINDy is an experimental NVIDIA/CUDA engine for SINDy-style sparse
equation search. It compiles small symbolic feature cohorts, evaluates many
runtime leaf settings on the GPU, and directly accumulates the statistics
needed for ridge, STLSQ, and validation scoring.

Instead of building a secondary feature matrix such as:

```text
[u, u_x, u_xx, u*u_x, sin(u), ...]
```

it evaluates generated features inside a CUDA Gram/statistics kernel and writes
only compact outputs:

```text
X^T X
X^T y
sum(X)
sum(y)
sum(y^2)
```

The project was previously named `implicit-sindy`. The package distribution is
now `fused-sindy`, and the preferred Python import is `fused_sindy`. The
historical `implicit_sindy` Python package and `implicit_sindy.h` C API remain
available so the current implementation namespace does not change under users.

## Status

This is a low-level, performance-oriented prototype. It is meant for technical
users, PyTorch integrations, and LLM-assisted search scripts that can build on a
clean CUDA/C99 API. It is not yet a polished scientific estimator package.

Use FusedSINDy when:

- primitive data already lives in PyTorch CUDA tensors;
- row count, grid samples, trajectories, or validation samples are large;
- generated feature matrices would be expensive to materialize repeatedly;
- you want to search many AST structures and many runtime leaf settings;
- NVIDIA/CUDA specificity is acceptable.

Prefer PySINDy, PDE-FIND-style workflows, or PySR first when the candidate
library is small, CPU portability matters, or the main need is mature modeling
ergonomics rather than fused CUDA throughput.

## Supported Scope

FusedSINDy is intentionally NVIDIA/CUDA-specific. The implementation depends on
PTX, virtual registers, nvPTXCompiler, nvJitLink, cubins, CUDA Driver module
loading, and patching compiled CUDA function bodies. These are not portability
details; they are the mechanisms that make the workflow possible.

The tested path is:

```text
Linux
NVIDIA GPU
NVIDIA driver recent enough for the target GPU
PyTorch CUDA wheel
CUDA Python/JIT packages pinned by this project
```

CPU-only execution, AMD/ROCm, Apple Metal/MPS, and generic accelerator backends
are out of scope.

## Core Model

The user provides primitive feature columns and target columns:

```text
primitive features:  u, u_x, u_xx, v, v_x, ...
targets:             u_t, v_t, ...
```

A compiled cohort contains 32 generated features. Each generated feature is a
fixed depth-3 binary AST with 8 leaves. The AST stores the operation shape.
Runtime settings decide whether each leaf is a primitive feature column or an
`f32` constant.

```text
compiled AST shape:
    (leaf0 * leaf1) + square(leaf2)

runtime setting A:
    leaf0 = u
    leaf1 = u_x
    leaf2 = 0.5

runtime setting B:
    leaf0 = u_xx
    leaf1 = 2.0
    leaf2 = u
```

This separation is the main amortization lever: compile expression structure
once, then evaluate many leaf/constant settings for that structure.

## Canonical Workflow

The intended search loop is:

1. Build primitive feature tensors and target tensors in PyTorch.
2. Generate AST cohorts, with 32 ASTs per cohort.
3. Generate many runtime settings for each cohort. Large settings batches should
   usually be generated by a small CUDA kernel, not Python loops.
4. Compile cohorts into CUDA modules with the patched AST compiler.
5. Launch fused Gram/stat kernels on training data.
6. Solve ridge or STLSQ sweeps from the raw Gram/stat outputs.
7. Launch the same Gram/stat kernels on validation data.
8. Score validation MSE from validation stats plus solved coefficients.
9. Keep sparse, low-MSE candidates and mutate/evolve the next generation.

There is no built-in k-fold aggregation path in the current API. If a user wants
k-fold behavior, Python can materialize or slice each split and run the same
`gram -> solve -> mse` path per split.

## Installation

Install a CUDA-enabled PyTorch wheel first, then install this repo:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install torch --index-url https://download.pytorch.org/whl/cu132
python -m pip install /path/to/fused-sindy
```

The base package depends on:

```text
cuda-core==1.0.1
nvidia-cuda-nvrtc==13.2.78
nvidia-nvjitlink==13.2.78
```

Build isolation also installs the matching CUDA runtime and nvPTXCompiler
packages:

```text
nvidia-cuda-runtime==13.2.75
nvidia-nvptxcompiler==13.2.78
```

PyTorch CUDA wheels normally choose the matching `cuda-bindings` major. If
installing without PyTorch, use an explicit CUDA Python extra:

```bash
python -m pip install '/path/to/fused-sindy[cu13]'
python -m pip install '/path/to/fused-sindy[cu12]'
```

See [docs/INSTALL.md](docs/INSTALL.md) for the full install notes.

## Minimal PyTorch Sketch

```python
import torch
import fused_sindy as fsindy

device = "cuda"
rows = 4096

u = torch.randn(rows, device=device)
ux = torch.randn(rows, device=device)
uxx = torch.randn(rows, device=device)

primitive = torch.stack([u, ux, uxx], dim=0).contiguous()
target = (-u * ux + 0.1 * uxx).reshape(1, rows).contiguous()

expr = fsindy.feature(0) * fsindy.feature(1)
ast, mask, words = fsindy.expression_to_ast_and_leaf_settings(expr)

asts = [ast] + [fsindy.padding_ast()] * 31
leaf_masks = torch.zeros((1, 32), device=device, dtype=torch.int32)
leaf_words = torch.zeros((1, 32, fsindy.NUM_INPUTS), device=device, dtype=torch.int32)
leaf_masks[0, 0] = torch.as_tensor(mask, device=device, dtype=torch.int32)
leaf_words[0, 0] = torch.as_tensor(words, device=device, dtype=torch.int32)

with fsindy.compile_gram_kernels(asts, kernels_per_module=1) as kernels:
    train = kernels.run_gram(primitive, target, leaf_masks, leaf_words)

with fsindy.RidgeSolver(device=device) as solver:
    alphas = torch.tensor([1.0e-6], device=device, dtype=torch.float32)
    thresholds = torch.tensor([1.0e-3], device=device, dtype=torch.float32)
    solved = solver.solve_stlsq(train, alphas, thresholds, row_count=rows)
```

For real searches, use separate train and validation Gram launches, then call
`solver.score_validation_mse(...)`.

## Repository Layout

```text
include/
    Public C99 API. Users include implicit_sindy.h.

src/
    C implementation files and internal STB-style compiler implementation.

cuda/
    Maintained CUDA kernel sources and headers.

python/
    PyTorch/nanobind package. The preferred import is fused_sindy; the
    implementation namespace remains implicit_sindy.

examples/
    Runnable PyTorch examples and search sketches.

test/
    C tests, Python tests, and benchmark programs.

tools/
    Build-time generators and smoke-test scripts.

descriptions/
    Minimal Stack PTX operation descriptions used by the AST compiler.

thirdparty/
    Vendored single-header dependencies:
    stack_ptx.h, ptx_inject.h, cubin_function_patch.h, incbin.h.

docs/
    Architecture, install, API, search, numerics, and performance notes.
```

## Performance Snapshot

These are local records, not portable claims. They are included so users can
understand the tradeoffs.

Compilation strategy comparison on an RTX 5090 workstation, 240 modules, 12
workers, 4 Gram kernels/module:

| Pipeline | Wall ms | Gram kernels/s | AST features/s |
| --- | ---: | ---: | ---: |
| Full dynamic Gram injection | 27400.022 | 35.036 | 1121.167 |
| nvJitLink object-link prototype | 10060.998 | 95.416 | 3053.375 |
| Current cubin-function patch path | 1644.552 | 583.744 | 18679.860 |

Current package compile scaling, 512 modules and 4 Gram kernels/module:

| System | Workers | Compile ms | AST features/s |
| --- | ---: | ---: | ---: |
| RTX 5090 + Ryzen 9900X | 12 | 2275.620 | 28799.190 |
| RTX 5090 + Ryzen 9900X | 24 | 1897.167 | 34544.147 |
| GH200 | 32 | 1409.292 | 46502.770 |
| GH200 | 64 | 941.264 | 69625.533 |

Runtime pipeline on RTX 5090, 4 cohorts, 2048 settings/cohort, 131072 train
rows, 65536 validation rows, 1 RHS:

| Solve | Total best ms | Train Gram ms | Validation Gram ms | Solve ms | MSE ms | Settings/s |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| STLSQ | 633.107 | 421.541 | 211.074 | 0.344 | 0.147 | 12939.365 |
| POSV | 633.153 | 421.572 | 211.211 | 0.256 | 0.115 | 12938.412 |

The solver and MSE kernels are tiny relative to Gram construction at this row
count. The current patch path gives up some runtime throughput compared with a
fully inlined generated Gram kernel, but it greatly reduces hot-path structural
compile time. See [docs/PERFORMANCE.md](docs/PERFORMANCE.md).

## Development

Native C/CUDA build:

```bash
cmake -S . -B build \
    -DCMAKE_BUILD_TYPE=Release \
    -DIMPLICIT_SINDY_BUILD_TESTS=ON \
    -DBUILD_PYTHON_BINDINGS=OFF \
    -DIMPLICIT_SINDY_BUILD_SOLVER=ON \
    -DIMPLICIT_SINDY_SOLVER_USE_NVRTC=ON

cmake --build build -j
ctest --test-dir build --output-on-failure
```

Python tests after installing the package in a CUDA-enabled environment:

```bash
python -m pytest -q test/python
```

The CMake options and C symbol names still use `IMPLICIT_SINDY` /
`implicit_sindy_*` for ABI continuity.
